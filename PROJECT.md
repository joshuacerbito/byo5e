# byo5e — architecture reference

A map of the codebase for anyone starting cold. Structure and conventions
only: no changelog, no current work, no commit history. If something here
stops being true, edit the line.

## What it is

A Vite + React 18 single-page app: a wizard that builds a D&D 5e character
from SRD data, and a phone-first character sheet you use at the table. No
react-router, no state library, no UI kit — the hand-rolled equivalents are
deliberate, and each one says why in its own header comment.

```
npm run dev            vite dev server
npm run build          production build
npm run check          static checks (scripts/check.mjs)
npm run check:content  drives both SRD packs through the content mapper in node
npm run check:export   renders the iOS raster export in headless Chromium
npm run build:packs    regenerates src/packs/*.json from a 5etools-src checkout
```

## The shape of it

`src/main.jsx` mounts one component — `CharacterCreator` — inside an
`ErrorBoundary`, with the whole stylesheet injected as a `<style>` tag above
it, so the fallback still has CSS when the app itself is what failed.

`src/lib/router.js` is the router: read `location.pathname`, listen for
`popstate`, `navigate()` pushes or replaces. Routes are `/` (splash), `/create` (the wizard),
`/sheet`, `/rulesets`, `/account`, `/terms`, `/privacy`. A direct load or
refresh of a non-root path only resolves because the host rewrites unknown
paths to `index.html` — `wrangler.toml` sets
`not_found_handling = "single-page-application"` for Cloudflare Pages.

`CharacterCreator.jsx` is the whole wizard and, despite the name, the app's
top-level component: it owns every route branch, all character state, and
the `sheetCtx` object described below. It is large. Reach for grep, not a
full read.

The wizard's steps are listed in `src/lib/steps.js` — Ruleset, Species/Race,
Class, Abilities, Background, (Spells), Inventory, Player Info, Summary. The
Spells step only appears for a caster. Ability-score improvements and feats
are picked inside the **Class** step, not a step of their own.

## Where the UI lives

| File | What is in it |
| --- | --- |
| `CharacterCreator.jsx` | Every wizard step, all character state, route branching |
| `components/Sheet.jsx` | The post-wizard sheet ("Done" lands here): Stats / Actions / Inventory / Features / Bio / Settings screens |
| `components/SheetSummary.jsx` | The Summary step's on-screen version of the same data |
| `components/Section.jsx` | The shared collapsible panel (`Section`) and its Show More/Less control |
| `components/Accordion.jsx` | The Sheet's expanding-row list, plus its expand-all section header |
| `components/CoreTraits.jsx` | The Class step's opening traits panel |
| `components/MasteryPicker.jsx` | Weapon Mastery search-and-add picker (2024 only) |
| `components/ActionsPanel.jsx`, `components/FeaturesPanel.jsx` | Attacks/spells and features lists |
| `components/FeatureBlocks.jsx` | Renders a feature's structured `blocks` (paragraphs, lists, tables) |
| `components/Drawer.jsx` | The Sheet's right-hand detail drawer |
| `src/styles.js` | **All** CSS, as one exported template literal |

`Section.jsx` and `Accordion.jsx` look similar and are not
interchangeable. A `Section` is a page section: one panel, a header with a
chevron, and a collapsed state that keeps every heading inside it and hides
only the prose and the resolved values. An `Accordion` is a row in a list
of rows, several to a screen, with a section header that opens all of them
at once. Wizard panels use `Section`; the Sheet's feature and action lists
use `Accordion`.

`ActionsPanel` and `FeaturesPanel` are rendered by both `Sheet.jsx` and
`SheetSummary.jsx`, which is why they take a `ctx` rather than reading
state: both are handed the same `sheetCtx` the export routes read, so a
field missing in one is missing in all of them.

## Data

```
src/packs/srd-5.1.json   2014 rules (SRD 5.1)
src/packs/srd-5.2.json   2024 rules (SRD 5.2)
```

**Never hand-edit a pack.** They are generated by
`scripts/build-srd-pack.mjs` from a local `5etools-src` checkout (itself
gitignored), records kept verbatim in 5etools shape, and the build is
deterministic — a re-run over the same checkout is byte-identical.

`src/content/` is the mapper layer, and the only part of the app that knows
5etools shape exists. `buildContent(pack)` is pure: hand it a parsed pack,
get back view models with named fields, no `{@tag}` markup and no
pipe-delimited references. That purity is what lets
`scripts/check-content.mjs` drive the same code from node.

- `content/load.js` — the browser entry point; the only module that
  `import()`s a pack, lazily and per edition
- `content/index.js` — `buildContent`, and the `optionIdOf` minter that
  gives every choosable option a stable id
- `content/classes.js`, `ancestry.js`, `backgrounds.js`, `items.js`,
  `spells.js`, `feats.js`, `options.js` — one builder per kind
- `content/prof.js` — normalises every proficiency block (skills,
  languages, tools, weapons) into `{ fixed, choices }`
- `content/entries.js` — turns 5etools entry trees into `blocks`

A reference the pack cannot satisfy becomes a warning in
`content.warnings`; the record around it is still emitted. Warnings, not
throws.

`src/rules/` holds edition-neutral rules maths — `abilities.js`,
`progression.js`, `combat.js`, `multiclass.js`, `prereq.js`, `choices.js`,
`effects.js`. `src/lib/` holds app plumbing: `storage.js` (the localStorage
save and the export envelope), `derive.js`, `sheetEntries.js`,
`sheetHtml.js` (the printed sheet), `currency.js`, `sync.js`.

## Two editions, one app

The 2014/2024 split lives almost entirely in **pack content shape**, not in
component code. The mapper reads whichever shape a record is in and emits
the same view model, so a class knows its own `subclassLevel` (1, 2 or 3
depending on class and edition), a species knows whether its ability
increases exist at all, and the UI never asks which edition it is in.

Before writing an `edition === "2014"` branch, check whether the difference
is already carried by the data. Genuine app-level branches are rare — the
multiclass ability prerequisites are one.

Corollary for anything data-shaped: read the pack before believing the UI.
`node -e` over `src/packs/*.json` settles what a race or class actually
grants faster than reasoning about the component that renders it, and the
two disagree more often than you would expect.

## Verifying a change

Three layers, each catching what the others cannot:

1. **`npx vite build`** — syntax and imports. Fast, and blind to everything
   else. It will happily build a page that throws on render.
2. **`node scripts/check.mjs`** — parses every module, resolves imports,
   finds unbound identifiers, and **fails on a `className` with no matching
   CSS rule** (an unused rule is only a warning). Since all CSS is one
   template literal in `styles.js`, markup and stylesheet have to move
   together, and this is what enforces it.
3. **Playwright** — the only layer that sees render order, conditional
   rendering and runtime state. Bugs that reach a real browser and nothing
   else: a crash from a value that is undefined only in one edition at one
   level, a section that collapses away a control the player still needs,
   a panel rendering above the level that earns it.

Playwright is in `node_modules` but there is no suite: drive a dev server
with a throwaway script, and keep the script **inside the repo** so
`node_modules` resolves. Delete it and any screenshots when done.

Two traps worth knowing before they cost an hour:

- A backtick inside a CSS comment in `styles.js` ends the template literal.
  The build does not catch it; the app breaks at runtime.
- A stack trace from the vite dev server names lines in the **transformed**
  file, not the source. `curl -s http://localhost:PORT/src/File.jsx` and
  read the line the trace actually named.

## Working in this repo

The hive shares **one working tree**, not a clone per agent. Someone else's
uncommitted work can be sitting in the same files.

- Stage explicit paths (`git add src/components/Section.jsx`). Never
  `git add -A`, never `commit -a`.
- Check `git diff --cached` before committing. A file you did not touch
  this session is somebody's work in progress; leave it.
- Re-read a file before editing it. What you saw an hour ago may not be
  what is on disk now.

Some header comments cite a `CLAUDE.md` that is gitignored and not present
in the tree. Treat those references as historical; this file is the one
that ships.
